# DEAPack shadow method ontology

This directory is the first machine-readable projection of the DEAPack method
universe. It is deliberately a **shadow registry** while the vocabulary and
migration checks settle.

The normative human registry remains [`../METHODS.md`](../METHODS.md) during
this phase. The files here do not alter the public catalog, do not make a
planned method executable, and are never parsed in a per-DMU solver path.
The `2.0.0rc1` governance target, represented by shadow-registry manifest
`2026-08-03-shadow.58`, contains 67 machine method records: 63
implemented/public records (62 public `method_id` entries and 1 public
`preset_id` record for APZ), and 4 deferred non-public prototypes retained for evidence
governance:
`analysis.mpss.banker_1984` and
`analysis.capacity.physical.fare_grosskopf_kokkelenberg_1989`, together with
`evaluation.super.ap_radial` and `evaluation.cross.crs`.
The same checkpoint contains 43 typed relationship records. Three explicit
Malmquist reference-policy relations connect adjacent contemporaneous,
full-sample global, and adjacent-pair biennial designs without promoting each
information policy to a separate primary method family.
The five constructor/reporting `specialization_id` entries and the other seven
`preset_id` entries remain catalog identities rather than being promoted to
duplicate machine methods. Four classic-radial presets reuse the
`static.radial` machine record; the output-oriented CRS FGNZ core preset
reuses `productivity.malmquist.adjacent_geometric`; the 1982 and 1983
multiplicative source presets reuse the single `static.multiplicative` machine
record and compiler. APZ instead has its own public preset record because its
capped-bad-output technology is an auditable source-defined composition rather
than a constructor-only recipe. The public catalog therefore contains 75
identities: 62 `method_id`, 5 `specialization_id`, and 8 `preset_id`
entries.
Record parity is not a claim that every method has the same validation depth.
All 63 implemented/public records have a direct execution benchmark and now
also carry a claim-scoped `analytically_derived`, `reproduced`, or
`cross_implemented` oracle status; none remains `not_located`. The four
prototype records have internal tests and benchmarks, but their
defining-source and independent-oracle gates remain open and their release
disposition is `deferred_to_next_version`. A benchmark is performance and
execution-contract evidence; it never substitutes for a defining source or
an independent numerical oracle, and an analytical certificate never
masquerades as a published-table reproduction.

Oracle status keeps evidence claims separate. `analytically_derived` requires
a typed exact certificate, an independently compiled validation path, and
explicit false values for both `published_reproduction` and
`production_compiler_reused`. It therefore supports independent numerical
verification without masquerading as a literature-table reproduction. Each
certificate claim names its evidence kind, resolvable pytest nodes, parameter
and result scope, reference population, data domain, and fixture dimensions;
an exact score proof cannot silently certify a broader slack, reference, or
data contract.

A `reproduced` or `cross_implemented` record may also carry an optional
claim-scoped analytical certificate when a source-defined extension has no
published numerical table. In that mixed-evidence case, the record-level
status continues to describe only the reproduced or cross-implemented
claims; the certificate's exact bounds, fixtures, and result components
govern only its named analytical claims. Candidate and `not_located` records
cannot carry such a certificate. At this checkpoint, every record that carries
an analytical certificate is classified `analytically_derived`; each claim
still remains limited to the parameter, result, reference, and data scope
declared inside that certificate.

## Scope

Each method record has exactly the eleven composition axes defined by the
unified framework:

```text
context
graph
data_roles
technology
estimator
reference
performance
valuation
evaluation_protocol
analysis
uncertainty
```

Result contracts, validation evidence, software backends, and documentation
placement are metadata over that composition. They are not additional study
axes.

Typed A--D relationships are stored separately because equivalence is a
directed statement between two specifications. Dependency and implementation
relations such as `composes`, `requires`, `shares_compiler`, and
`exact_reduction` do not receive an artificial A--D level.

Historical aliases that do not define a second executable composition are
declared under the canonical method's `names` block. For example,
`static.erg` resolves to the canonical standard non-oriented SBM record only
on its registered equivalence domain; it is not a second catalog method.

## Files

```text
schema/
    method-record-v1.schema.json
    relation-record-v1.schema.json
methods/
    <method category>/
relations/
registry-manifest.json
```

The schemas use JSON Schema Draft 2020-12. Development tests validate every
machine record against the complete schema with the optional test dependency
`jsonschema`; this never adds a DEAPack runtime dependency. Additional
cross-record tests resolve aliases and typed relations, check evidence
locators and documentation placements, and compare implemented public records
with the Python discovery catalog. The `placement.book` array remains in the
schema for compatibility but is empty in every method record while the book is
withheld from this repository. Public catalog entries therefore advertise only
live package documentation.

`status.publication_scope` separates implementation maturity from reader
publication. It is required for productivity, network, dynamic, panel,
heterogeneity, evaluation, diagnostics, decision, inference, and uncertainty
records.
These categories use
`handbook_core`,
`supporting_reference_policy`, `handbook_sensitivity`, or
`documentation_only`; a planned or prototype record in one of these
categories must use `next_version`. The names containing `handbook` are retained
as compatibility metadata for the established editorial classification; they
do not assert a live book path or publication in this repository. Placement
roles describe only locations that are actually present.

For example, Global Malmquist is a `supporting_reference_policy` inside the
ordinary Malmquist family route, and Oh GML is a bounded `sensitivity` beside
the CFG environmental account. Within network DEA, the Färe--Grosskopf,
Kao--Hwang, Chen, and Cook entries are core accounts inside one connected-
organization family rather than four independent primary families. The
Tone--Tsutsui network SBM is the second retained network family. Sequential,
environmental-network, dynamic-network, and multiperiod-aggregation leaves
remain discoverable as `documentation_only`. None of these compatibility scope
choices changes API maturity, numerical verification, or documentation
placement.

The current heterogeneity core is deliberately singular: the implemented
O'Donnell--Rao--Battese radial group/metafrontier account. Its MTR/TGR is an
opportunity-proximity ratio (`higher_is_closer`), not a second managerial
efficiency score. Non-radial, environmental, latent-group, nonconvex-union,
and productivity metafrontiers remain separately source-gated future leaves.

Evaluation is now governed by the same publication contract. The three
source-qualified public leaves--Tone super-SBM, Ray directional
super-efficiency, and Liang--Wu--Cook--Zhu game cross-efficiency--remain
`documentation_only`: they are available, tested research procedures but do
not become separate primary-family routes. The ordinary CRS
cross-efficiency and Andersen--Petersen radial reconstructions remain
non-public prototypes scoped to `next_version`. The reserved `decision`
category is governed before it acquires records: any future planned or
prototype decision procedure must be `next_version` and cannot imply a
current API or published documentation page.

The first governed deterministic diagnostic is
`analysis.reference_frequency.selected_plan`. It consumes one complete,
certified peer account from a static convex global cross-section and launches
no optimization. It counts only reported active peer edges strictly above the
source result's `peer_tolerance`; that threshold and the complete denominator
remain result metadata. The integer `reference_frequency` equals self-reference
plus other-reference counts; `reference_rate` divides that total by the number
of evaluated organizations. It deliberately makes no alternate-optimum, global-
reference-set, influence, outlier, ranking, or inferential claim. Its
`handbook_sensitivity` compatibility status embeds that safeguard in study
design rather than promoting diagnostics into a separate model route.

Evidence-source roles are deliberately narrow. `defining` freezes the
method's own formulation; `equivalence` supports an identity claim;
`predecessor` records lineage without treating an earlier formulation as the
current leaf; `critique` documents a published limitation or correction;
`review` supplies synthesis; and `implementation` identifies an independently
executable formulation or oracle.

## Source-of-truth migration

The intended final direction is one-way:

```text
method ontology
    -> implemented/public Python catalog projection
    -> generated registry and compatibility tables
    -> generated documentation discovery tables
```

During the shadow phase, consistency tests require exact two-way parity
between the 63 implemented/public machine records and the corresponding
machine-backed catalog identities: 62 public `method_id` entries and the APZ
public `preset_id`. A public record without a catalog identity and a catalog
method without a public record both fail validation. The four retained
prototype records are deliberately excluded from that projection: a machine
record can preserve code provenance and an evidence gate without granting a
public catalog identity. No generator yet writes `src/deapack/catalog.py` or
`specs/METHODS.md`.

`ontology_schema_version` versions this static record structure. It is
separate from `REGISTRY_SCHEMA_VERSION`, which versions the compact
eleven-axis `expanded_spec` attached to a fitted result.

## Status discipline

- `implemented` plus `public` means the record is eligible for the eventual
  catalog projection.
- `prototype` means code or a formulation may be under active development but
  is not public catalog evidence; its API status must be `none` unless a
  separate experimental-release decision has been recorded.
- `planned` and `prototype` records must not appear in the current public
  catalog.
- An implemented umbrella does not automatically promote its planned
  variants or presets.
- A Level A relation requires evidence for the feasible set, objective or
  exact value transformation, targets and peers, parameter domain, and a
  regression test.

## Contribution rule

Add evidence before promoting status. A new record should state its economic
question, all eleven axes, data and invariance domain, target guarantee,
backend capabilities, source and oracle status, required tests, and intended
documentation placement. Equal rankings or shared matrices are not alias
evidence. A current-release candidate needs both an original or authoritative
defining source with frozen source-native equations and economic semantics,
and an independent numerical oracle or equivalent exact executable
certificate. If either side cannot be closed, the candidate remains in a
next-version source protocol as `deferred_to_next_version` and receives no
public catalog identity. A pre-existing code-bearing candidate may retain a
non-public `prototype` machine record solely to preserve its composition,
implementation provenance, and explicit evidence gate. Such a record must
have API status `none`, no public API placement, and a locator to its
controlling source protocol; it is inventory for future audit, not a
current-release method claim.
